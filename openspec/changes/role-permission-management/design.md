## Context

当前系统仅支持简单的多角色管理，权限硬编码在前端逻辑中。后端缺乏对 API 及数据资产的动态权限校验。我们需要建立一套统一的、属性敏感的权限模型。

## Goals / Non-Goals

**Goals:**

- **动态权限校验**: 实现基于角色的动态菜单、按钮以及接口级权限。
- **数据隔离**: 支持“本人/科室/全院”四级数据范围隔离。
- **高可用设计**: 权限数据进行常驻 Redis 缓存，提升鉴权效率。
- **UI 易用性**: 左侧列表 + 右侧标签页的交互布局。

**Non-Goals:**

- 本次不涉及多租户跨库隔离设计。
- 角色继承逻辑在第一阶段仅做模型预留，暂不实现复杂的自动向下传播。

## Decisions

### 1. 数据模型设计 (RBAC + ABAC 混合)

- **原因**: 传统的 RBAC 很难处理“本科室”这类基于属性的权限（Data Scope）。
- **具体方案**:
  - `SysRole` 表增加 `data_scope` (int) 字段来标识权限范围（1=全部，2=本机构，3=本科室，4=本人）。
  - `SysMenu` 表不仅管理菜单，也作为权限的基础，增加 `perms` 权限标识和 `api_path`。

### 2. 鉴权缓存策略

- **方案**: 在 `Auth` 中间件中，根据 `UserID` 缓存其拥有的所有 `Permissions` 和 `DataScope` 到 Redis。
- **失效机制**: 修改角色权限或分配用户角色时，主动清除对应用户的 Redis 缓存。

### 3. 前端权限指令

- **方案**: 封装 `v-hasPerm` 指令及全局 `checkPerm` 函数。
- **理由**: 组件内控制比全局更灵活，且能有效减少不必要的按钮渲染。

### 4. 角色复制逻辑

- **方案**: 数据库层面使用事务开启克隆：复制角色基本信息 -> 关联其所有菜单及数据权限。不包含原角色的用户列表。

## Risks / Trade-offs

- **[Risk] 权限缓存不一致** → [Mitigation] 使用 Redis 发布订阅或主动失效机制，确保权限实时生效。
- **[Risk] 极其复杂的菜单级联勾选性能** → [Mitigation] 前端树组建开启 `check Strictly` 模式，手动处理父子依赖。

## Migration Plan

- **初始化**: 提供基础 SQL 脚本，包含“超级管理员”、“普通医生”、“前台护士”三个预设角色及其对应的完整菜单权限。
- **数据迁移**: 将现有的 `admin` 账号自动关联至“超级管理员”角色。
