## 上下文

本项目《医院全科随访系统》目前已经具备了基础的数据库模型定义和认证机制初稿。当前需要实现一个标准的、可用于生产环境的用户管理界面及其配套的后端接口。系统采用前后端分离架构（Go Gin / React），需要确保用户管理功能符合整体的安全规范和目录结构。

## 目标 / 非目标

**目标:**

- 实现用户账号的增删改查（CRUD）及分页搜索。
- 支持用户启用/禁用状态切换。
- 实现管理员重置用户密码的功能。
- 支持为用户分配系统角色（关联 `user_roles` 表）。
- 确保用户基础信息变更时，关联的 `doctors` 档案信息保持同步（或由同一套接口管理）。

**非目标:**

- 实现复杂的审批流程。
- 集成第三方 LDAP 或 OAuth 登录（本阶段仅支持数据库认证）。
- 实现精细到字段级的数据脱敏。

## 技术决策

### 1. 后端接口设计 (Go Gin)

- **RESTful API**:
  - `GET /api/users`: 分页查询用户列表（支持模糊匹配和科室过滤）。
  - `POST /api/users`: 创建新用户（同步在 `users` 和可能在 `doctors` 插入记录）。
  - `PUT /api/users/:id`: 编辑用户信息。
  - `DELETE /api/users/:id`: 逻辑删除用户。
  - `PUT /api/users/:id/status`: 快速切换用户状态。
  - `PUT /api/users/:id/password`: 重置密码。
- **事务处理**: 在 `Service` 层使用事务处理 `users` 与 `user_roles` 的多对多更新。

### 2. 前端架构 (React + shadcn/ui)

- **列表页**: 使用 `DataTable` 组件，集成后端搜索、排序和分页。
- **表单管理**: 使用 `react-hook-form` + `zod` 进行数据验证。
- **状态管理**: 简单交互使用 `useState`，列表数据缓存使用 `React Query`。

### 3. 数据一致性

- **Users ↔ Doctors**:
  - 决策：在用户管理界面，若该用户具有医护人员属性，则同时收集并维护 `doctors` 表所需的信息（如职称、擅长领域）。
  - 理由：减少管理员在不同菜单间切换的操作负担。

## 风险 / 权衡

- **[风险] 软删除后的唯一约束冲突** → [缓解] 在查询和判断唯一性时，始终带上 `deleted_at IS NULL` 条件。并在数据库层面，若需要多端冲突，建议对重复账号名在删除时增加特殊标记（如加上时间戳后缀），但本项目初步采用在业务层逻辑控制。
- **[风险] 角色变更生效延迟** → [缓解] 角色信息存储在 JWT 或 Redis 缓存中，需在角色变更后使对应的 Token 失效或强制刷新。
- **[风险] 密码明文传输** → [缓解] 前端仅做基础格式检查，后端使用 `bcrypt` 进行哈希存储。严格禁止在任何日志中记录用户密码。

## 迁移计划

- 准备初始化 SQL 脚本：确保预置必要的科室和基础管理员角色。
- 逻辑删除处理：确保现有查询逻辑已适配软删除字段。
